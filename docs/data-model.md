# Phase 2 data model

All monetary values use PostgreSQL `NUMERIC`, not floating point. `currency` is an
ISO-4217-style three-letter code, and rates express one unit of `currency` in
`base_currency`. Dates are calendar dates in the simulation/business timezone;
audit timestamps are timezone-aware UTC values generated by PostgreSQL.

## Relationships

- **LegalEntity 1-to-many BankAccount, LedgerEntry, Receivable, Payable, CashFlowForecast,
  and ForecastRun.** A legal entity owns its accounts and source records.
- **BankAccount 1-to-many LedgerEntry and CashFlowForecast.** A forecast account is
  optional because a scheduled flow may not yet be assigned to a bank account.
- **Receivable and Payable are source schedules.** `CashFlowForecast` stores the
  normalized forecast item and optionally points to exactly one source record.
  The application layer must enforce that `source_type` matches that source.
- **LiquidityScenario 1-to-many ScenarioCashFlowAdjustment and ForecastRun.**
  The adjustment bridge gives a scenario-specific date/amount change to a forecast
  item without mutating the baseline item.
- **ForecastRun 1-to-many ForecastPosition.** A run records one versioned,
  immutable calculation context and its daily positions.
- **ActualCashFlow optionally references CashFlowForecast.** This supports later
  forecast-versus-actual reconciliation while allowing unmatched actuals.
- **CurrencyRate** is independently effective-dated and unique per currency,
  base currency, and date.

The integer primary keys are internal joins. Each business table also has an
immutable, unique code (`ENT-...`, `BANKACC-...`, `CF-...`, `FCAST-...`, etc.);
the generator and service layer will produce those identifiers in Phase 3+.
